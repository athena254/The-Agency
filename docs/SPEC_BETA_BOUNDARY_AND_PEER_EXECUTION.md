# Beta boundary fixes and peer execution — approval checkpoint

Status: **proposed contract, not implemented or deployed**. Source revision: `07de00c886529bb712536d53a08e35ac869a09ba`. This document starts with the contained beta security fixes, then defines the architecture checkpoint for replacing the single authority implied by `AgencyOrchestrator`. Do not cherry-pick the unsafe `feat/beta-integration` WIP wholesale. This spec complements `SPEC_PEER_LATTICE_GOVERNANCE.md` (which supersedes central-governance claims in `SPEC_LATTICE.md`) and `SPEC_L2_TELEGRAM_BETA.md`; it does not assert peer consensus exists today.

Owner decisions after the initial checkpoint: **start with independently running, authenticated, known peers, each with its own store and versioned membership; federated peer-selected membership is a later phase.** Beta may use **bounded `web_search` only** after all identity, audit, privacy and budget gates pass; `web_fetch` and consequential actions remain off. These decisions do not select a quorum/failure model or authorize deployment. The Stage 1a strict-principal/search-bound fix was integrated locally on `main` as `a503037` and passed 905 offline Python tests; it is not wired into production beta execution.

## Plain English

Fix the beta door before inviting anyone: validate the person and private chat, limit requests, allow only bounded web search, and refuse to call a task successful if its audit record cannot be saved. Then replace the **single decision-making orchestrator** with locally running peer agents that authenticate each other and agree on consequential decisions. Butler/Telegram may deliver requests; neither can vote for peers. Until multiple independent peers can prove agreement and survive partitions, creation, policy changes, and other consequential actions stay off. A local scheduler may still coordinate *its own* read-only task, but is never a network-wide authority.

## Scope and non-goals

**Stage 1 — contained security fixes:** strict principal validation and default search bound, denial tests, then a beta-only fail-closed admission/tool/audit slice. Stage 1 permits bounded `web_search` for explicitly admitted users only; it does not enable `web_fetch`, memory tools, sandbox execution, agent creation, governance voting, or L2 capabilities. A beta task cannot be labeled completed without a durable audit completion record. Nonbeta behavior must not be silently changed.

**Stage 2 — peer architecture/protocol:** decompose the current class into a local request adapter/scheduler and independently running peer runtimes. It is **not** satisfied by merely renaming `AgencyOrchestrator`, moving methods to another singleton, sharing one SQLite file, or turning Butler into a leader. Implementation of consequential execution waits for a reviewed peer protocol, independently persisted peers, and fault tests.

**Out of scope now:** enabling `web_fetch` (DNS preflight is not connection pinning and synchronous DNS can block the event loop), deployment/restart/remote push, claiming fully decentralized governance, inventing quorum thresholds or Sybil resistance, importing an entire blockchain framework, or changing the active deployment tree. Legacy HTTP `/v1/message` and Agency API routes require an explicit exposure/authentication decision; do not treat Telegram admission as protection for them. **Release gate across every entrypoint:** until peer certificates and actuator checks exist, no consequential route may create/revoke agents, change policy, cast a decisive vote, run a bridge with side effects, or authorize execution. In particular, `/v1/governance`'s owner-token `user` vote still invokes an immediate override, and `/v1/agents` mutations have no equivalent owner dependency (`src/agency/api/routers/governance.py:18-29,103-113`; `src/agency/api/routers/agents.py:89-138`; `src/agency/lattice/governance.py:144-149`). Inventory and explicitly disable/authenticate each legacy route before any beta invitation; a Telegram-only guard is insufficient.

## Stage 1 contracts (1a locally implemented; 1b awaits approval)

1. `BetaPrincipal(telegram_user_id: int, private_chat: bool)` has **no default** for `private_chat`; construction rejects bool/nonpositive/noninteger ID and any non-boolean scope. Only trusted Telegram admission code creates it from validated `from.id`, `chat.type == "private"`, matching `chat.id` and invite-list membership. Untrusted text, `sender`, LLM tool args, and metadata cannot mint the grant. `BetaToolPolicy` checks `principal.private_chat is True` and validates the object type; denial is non-executing and auditable.
2. `BetaToolPolicy(max_results=N)` checks the **effective** count (`args.get("max_results", 5)`) and rejects bool/nonint/out-of-range. A configured `N < 5` denies omitted count (the tool's unchanged default is five); an explicit count at or below `N` remains permitted. Do not silently raise `N` to five. Bound search query length; never log query content. Only `web_search` is registered/advertised in beta and `web_fetch` remains unavailable even by direct call. Existing nonbeta tool registry remains legacy-open only in explicitly nonbeta configurations.
3. `TelegramHandler` applies one shared admission and request-budget step in `handle_update` and `process_message`, before Butler/LLM/tool access. Only trusted polling and secret-verified webhook ingress may construct an admission claim; standalone caller-supplied message dicts (including direct `process_message` calls) are untrusted and cannot mint one. Bind the claim to transport provenance and Telegram `update_id`/chat/user IDs. Redelivery of the same update reuses one durable reservation and does not duplicate the tool call; Telegram delivery is at-least-once and a crash after send but before durable acknowledgement **can duplicate the reply**. Rejected unauthenticated/invalid requests do not consume another user's budget. Deterministic help/status handling is a separate configurable cost policy; no hidden live-model fallback. Per-user request and model budgets need explicit values and persistence semantics before inviting users (open decision below).
4. Beta startup requires explicit enabled mode, nonempty ID allowlist, a durable audit path (not `:memory:`), and a policy-wired tool layer; missing/malformed config refuses beta startup. The webhook is disabled for beta unless a real Butler lifecycle and same boundary are exercised. The bot's `src/telegram_bot.py` construction must pass consistent beta configuration to each component; a Telegram-only beta gate cannot imply orchestrator/tool gating. API exposure must be addressed independently.
5. For read-only beta search, persist a sanitized **pre-call intent** record before tool invocation and a sanitized completion/failure record before claiming success. Audit append failure at either point fails the task/reply and forbids a success memory write; never catch and continue as WIP does. External requests already sent cannot be rolled back: a post-call failure means **intent persisted, outcome unknown**, not a completion-audited outcome or fictitious rollback. Recovery must reconcile the event/task before more beta work is admitted. Define the crash/power-loss durability and tamper-evidence requirement explicitly: the current SQLite WAL with `synchronous=NORMAL` and append-only API alone do not guarantee either (`src/agency/kernel/audit.py:131-163,183-228`). Do not include prompts, search terms, raw outputs, credentials, or user message content in beta audit entries. Other sinks require separate policy: current Butler audits message/reply excerpts, task submission can mirror descriptions to Lattice, and search evidence can include a query (`src/agency/butler/service.py:258-296`; `src/agency/orchestrator.py:350-372`; `src/agency/tools/builtin/web.py:362-373`). Inventory logs, audit, task, Lattice, memory, evidence, and error sinks; decide what owner-scoped content may persist outside audit and test each sink. If append fails, return a fixed error and suspend further beta work until audit health recovers. Tool-level error handling and Butler must preserve status; never transform failure into success-shaped text.
6. A beta research result is completed only after the driver status is completed, at least one `web_search` step returns nonempty usable results, citations in the answer resolve to those results, and audit completion is durable. A search attempt that returns an empty result list or an unsourced model final answer must be labeled honestly, not “research complete” (`src/agency/tools/builtin/web.py:352-373`; `src/agency/tools/driver.py:220-228`). Owner-scoped memory uses authenticated Telegram ID, never shared agent ID; read paths must be equally scoped or disabled. Tests must not use metadata as proof of owner. This is a privacy boundary, not peer-governance authority.

### Data flow / fields

`AuthenticatedIngress(transport, update_id) + TelegramUpdate → AdmissionClaim(telegram_user_id, private_chat=True, chat_id, transport, update_id, policy_version) → durable budget/update reservation → ButlerRequest(claim, user_input) → local execution adapter → ToolContext(beta_principal=claim-derived BetaPrincipal, task_id, agent_id) → ToolRegistry(BetaToolPolicy) → WebSearchTool → sanitized audit outcome → ButlerReply(status, text)`.

The claim is created only after Telegram transport authentication/admission and is never deserialized from arbitrary HTTP JSON as authority. `task_id` and audit event IDs are unique and idempotent across retry; scope memory by stable `telegram_user_id`. Define explicit `FAILED`/`INDETERMINATE` statuses and fixed user-facing text for audit/write/search failures. Request body, model output and privacy-sensitive query are absent from the beta audit payload. This is a proposed interface, not current code.

### Stage 1 acceptance tests

Use an isolated worktree and `AGENCY_LLM_PROVIDER=echo AGENCY_LLM_MODEL=echo`; never run the full suite against canonical tracked runtime `data/lattice.db`. Add focused failing regressions first, verify RED then GREEN, then full `pytest tests/ -q`, `ruff check src/ tests/`, `ruff format --check src/ tests/`, `mypy src/`, and `git diff --check`. Hermetic tests must prohibit live network/DNS and use injected transports/resolvers.

- `BetaPrincipal(id)` (missing scope) and `private_chat="false"`/`1` raise; positive ID plus literal `True` succeeds; negative, bool ID or group scope cannot run a tool.
- Default `max_results` against a configured cap smaller than five is rejected at policy boundary; explicit over-cap count is rejected; valid bounded search is allowed. Direct registry/factory construction cannot discard policy or accept nonbool verdicts.
- Both Telegram handler paths deny unauthorized/private-chat-invalid/budget-exhausted traffic before any Butler, model or tool call; eligible `/research` reaches only search with a real principal. Unknown commands and creation requests never reach model/tool. Webhook cannot claim beta readiness without Butler wiring.
- Inject audit append failure before tool call and after search but before reply: no successful task, success response, or memory entry; explicit fixed error, no exception body leak. Reopen the durable audit to prove successful records survive restart. A searchless final answer is failed, and two owner identities cannot read one another's task memory.
- Verify legacy/nonbeta unaffected; inspect all exposed HTTP routes for identity-bypass and keep unsafe ones disabled or authenticated rather than asserting the Telegram gate protects them.

## Stage 2 peer-execution architecture — no single orchestrator

### Authority boundaries

- `Telegram/Butler` = transport and human-facing interface only. A Telegram user may request work; that input is **not** a peer ballot or universal grant.
- `PeerRuntime(peer_id, local_store, authenticated_transport, policy_version)` = independent agent process with its own durable store and signing identity. Each peer verifies proposal/ballot provenance and computes a deterministic local decision from the same signed evidence. No peer is privileged solely by deployment location. LLM outputs are evidence/proposals, not authorization.
- `PeerLattice` = replicated authenticated event history and relationship graph. Local SQLite may cache a peer's events but cannot be the only global truth. Authenticated membership and a versioned affected-consumer snapshot are required for each consequential proposal. Bind the snapshot to an authenticated graph/epoch root with reasons for each affected member; each verifier recomputes/validates derivation and consumer notification/input evidence, and rejects forks or stale views. A proposer-supplied list alone is not proof of completeness.
- `LocalTaskScheduler` = optional local dispatch mechanism; it may schedule read-only tasks without voting. It cannot invent ballots, grant mutating capabilities, or decide peer consensus. Replace central orchestrator calls incrementally behind interfaces; do not tear out the running adapter before an alternative is proven.
- `PeerExecutionGrant` = proposal ID/version + action/resource + authenticated graph/epoch root + affected-set and policy hashes + voter certificate + expiry + idempotency key. A runtime executes a consequential action only after independent validation of that certificate against its own local state, and persists the grant/side-effect idempotency record first. Idempotency per proposal is not enough: require intersecting quorums across membership epochs, conflicting-proposal locks/finality and a resource-scoped monotonic fencing token verified at the **actual actuator** before each side effect. No raw `user`/`system` caller string bypasses this check.

### Protocol checkpoint (not selected yet)

Phase one uses **known authenticated peers with independent processes and stores**, a versioned membership set, and explicit membership-change approval under the current peer policy; no central membership administrator can silently add a voter. Specify, review and commit: peer identity and key rotation/revocation; relationship graph and affected-set snapshot derivation; proposal/event/ballot canonical serialization and signatures; membership epochs and anti-Sybil admission; explicit quorum and affected-consumer participation thresholds; expiration and equivocation handling; authenticated transport; event ordering/replay and deduplication; partition behavior and recovery; conflict policy; audit durability; side-effect idempotency; and observability of missing votes. A partition without valid agreement **fails closed** rather than allowing two sides to execute conflicting changes. Federated peer-selected trust groups are deferred until the known-peer safety model is proven. Until the quorum/failure choices are made, consequential governance stays disabled.

Consider alternatives rather than smuggling in a central service: a fixed-membership BFT validator set has explicit quorum-intersection reasoning but centralizes membership policy; federated quorums permit local trust choice but can form a small top tier and require careful intersection analysis; eventual CRDT/event replication alone cannot authorize conflicting consequential mutations. MLS can help group authentication/keying but is **not** a consensus or governance algorithm. References: [Tendermint consensus spec](https://docs.tendermint.com/master/spec/consensus), [federated quorum analysis](https://link.springer.com/article/10.1007/s00446-022-00430-0), [RFC 9420 MLS](https://datatracker.ietf.org/doc/html/rfc9420). No protocol choice is made here.

### Peer acceptance before enabling mutations

Run at least three **separate peer processes/stores** with at least two affected consumers; verify independent attributable ballots and identical derived outcomes with Butler stopped. Reject one-ballot pseudo-quorum, missing affected consumer, forged/duplicate/replayed ballot, stale policy/affected-set version, failed evidence/audit persistence, split-brain partition, and unilateral `user` override. Restart and heal partitions, replay out of order, revoke a peer, and prove convergence without duplicate side effects. Multi-peer tests and real transport identity review, not a local in-memory mock, are necessary before claiming decentralized governance. See `SPEC_PEER_LATTICE_GOVERNANCE.md:25-34`.

## Decision gates and next sequence

1. **Approval of Stage 1b and the peer protocol direction** plus beta scope (who is invited, search-only vs no tools, rate/model budget values, webhook/legacy HTTP exposure). Safe default until clarified: no new invitees, no new tool surface, beta deployment off, no consequential operations. The user's instruction to start fixes authorizes the contained Stage 1a changes, not a live rollout or an invented quorum.
2. Stage 1a: strict principal and effective search bound, with TDD and independent review, implemented locally on a separate fix branch. Stage 1b: trusted propagation, budget and durable audit with end-to-end failure tests remains pending this checkpoint. Separate branch/commit per slice; do not wire a partial security boundary into the live bot.
3. Review peer protocol choices—especially membership/quorum/affected consumers—before building distributed governance. Only then replace central authority incrementally; no claim of full decentralization from a renamed class or single-process tests.
4. Integration/release: full local checks, independent security review, then owner approval for push/deploy; verify deployment checkout, active poller, DB backup, rollback, and an owner-side smoke before any beta invitation.

Open questions: How are known peers enrolled and who can admit/revoke one under a peer-approved membership change? Must *every* affected consumer vote, or is a threshold permitted? What failure model (crash vs Byzantine) and tolerated faults determine the minimum peer count/quorum? What exact per-user request/model budgets and persistence requirement? Should legacy HTTP be disabled by default? `web_search`-only beta scope is chosen, but its admission/audit/privacy/budget gates remain open. None is silently decided by the current single-process implementation.
