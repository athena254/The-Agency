# Peer Lattice governance — corrected target contract

Status: architecture correction and acceptance contract, **not implemented**. This supersedes the *central single-source-of-truth/Butler vote override* interpretation in `SPEC_LATTICE.md` §§1,7 for future work. Preserve that older document as a record of the current single-process implementation; do not assert it already meets this contract.

## Plain English

The agents are peers. They propose, review, vote and decide together. The Lattice records *their* identities, relationships, evidence, ballots and decisions and lets independently running peers agree on the result; it is not a boss that chooses for them. If an agent's work is consumed by others, those consumers can submit feedback and participate when changes affect them. Butler is a translator between a person and those agents. It does not own agent policy, impersonate voters or manufacture consensus.

## Hard invariants

1. **No central authority:** no Butler, one orchestrator process, one privileged `system`/`user` string, database writer, or hidden super-agent can unilaterally authorize an affected-peer decision. A human may express a real authenticated preference only through an explicit, attributable input; it cannot stand in for another peer's vote. The governance protocol must remain deterministic when the conversational/model layer is absent.
2. **Explicit relationships:** peer identities are stable and cryptographically attributable or otherwise authenticated to the trusted runtime; an agent's consumers/affected peers are recorded as directed dependency/consumption relationships. Before proposing a change, the proposer snapshots a versioned affected-set with a reason for each member. Each affected consumer must receive an opportunity to contribute evidence/feedback/ballot; membership changes require a new proposal version, not silent voter substitution.
3. **Accountability:** each proposed decision references its subject agent, proposer, action, affected-set snapshot, evidence, deadline and policy version. A signed/attributed peer ballot has one voter, proposal version, decision, evidence, monotonic identity/sequence and idempotency key. Retain contradictory feedback and outcome evidence in the audit trail; a consumer can trace which peer supported or opposed a decision and update provider reputation through a reviewed policy. No auto-generated votes from natural-language Telegram messages.
4. **Decision rule:** deny execution while required affected-peer input is missing, identities are unverified, there is a conflict, evidence persistence fails, or the relevant network view is stale. An approval requires (a) a snapshotted eligible voter set, (b) participation threshold including affected consumers, (c) an explicit approve threshold, and (d) expiration/timeout and conflict handling. The exact threshold and how nonresponding peers affect liveness are **open policy choices**; until committed and tested, consequential decisions remain disabled. A single approving ballot may never count as multi-peer quorum merely because the denominator contains only cast votes.
5. **Distributed substrate:** independent peer processes replicate or reconcile the signed event history and deterministically derive the same decision from the same evidence. No one SQLite file or in-memory dict is a network-wide source of truth; local SQLite can be a peer's durable cache. A partition must not let different sides execute conflicting approved outcomes; on missing agreement, fail closed. Reconnect/replay must converge without duplicate side effects. Specify membership, transport authentication, ordering, replication and conflict policy before enabling mutations.
6. **Interface boundary:** Butler and Telegram/UI show proposal status, voter/evidence trail, missing affected inputs, and honest failure; they submit authenticated human requests, not agent ballots. An agent may accept work from Butler but its execution authority derives from peer policy and verifiable grants, not the caller string. Even a local prototype should not expose the old governance mutation route as if peer-consensus were live.

## Present code versus target

- `src/agency/lattice/governance.py` stores `_proposals` in memory, uses a process-local `asyncio.Lock`, mirrors proposal/vote/resolution best-effort, treats one approve as 100% of cast approve+deny weight, and has an immediate `user` override. These are not durable peer consensus or affected-consumer participation.
- `src/agency/lattice/models.py` has Vote and ConsensusProposal primitives but lacks an immutable affected-set snapshot, relationship reason and protocol/version-bound ballots.
- `src/agency/lattice/api.py` exposes proposal/vote methods but does not establish peer identity or synchronize decisions between autonomous nodes. Legacy Telegram creation synthesized approval; current beta guard blocks it, but policy is still not ready.
- `SPEC_LATTICE.md` calls the Lattice "central" and SQLite the single truth. This is an implementation constraint, not the target topology. Butler remains the user adapter and should not become the leader.

## Build slices and acceptance tests (not yet passed)

A. **Design/protocol checkpoint:** specify peer identity, consumer graph and affected-set derivation, proposal and ballot schema, quorum/timeout rule, trust boundaries, event authentication, membership change, replication and conflict resolution. Include failure modes and an adversarial review. Commit before implementation.
B. **Hermetic local peer simulation:** instantiate at least three separate peer runtimes/stores, with at least two affected consumers. Propose a change to a provider; verify all affected peers see the same immutable proposal, contribute independent ballots/evidence, and derive the same final decision without Butler in the loop. One ballot, forged vote, duplicate replay, missing required consumer, or backend audit failure must not approve.
C. **Network/fault proof:** partition peers, reorder/delay/replay messages, restart one node, revoke a peer, introduce conflicting proposals, and verify no split-brain execution, convergence after heal, durable attribution, and deterministic fail-closed behavior. Verify network transport identity and authorization independently of tests using mocks.
D. **Product wiring:** only after A–C, make UI/Telegram show affected parties, status, evidence and real explicit human input. No synthetic user/Butler ballots. Controlled rollout requires owner approval and live proof.

## Relationship to MVP

The local browser/Telegram/Butler interface work can proceed in isolated worktrees because it is only an adapter. It is **not a fully decentralized MVP** until the peer-governance tests above pass. Keep agent creation, policy changes and consequential actions off in both entrypoints meanwhile. Mark any demo as a UI/connector prototype, not the completed Agency architecture.
