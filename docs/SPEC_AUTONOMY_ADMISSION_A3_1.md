# A3.1 — Required gateway audit acknowledgement

Status: **APPROVED for direct assistant implementation and offline testing** after checkpoint `622e41b`; see `research-evidence/autonomy-a3-1-approval.json`. No runtime enablement or deployment approval.

## 1. Plain-English purpose

A gateway must not report a completed turn when a required audit write failed. If logging fails before routing/execution, do not start that work. If logging fails after execution, do not return the generated answer as a successful turn or save a successful conversation transcript. Say that the result could not be confirmed; do not automatically rerun it.

This is an offline maintenance repair, **not completion of A3 or permission for autonomous operation**. The evidence map and remaining gates are in `RESEARCH_AUTONOMY_ADMISSION_A3_20261016.md` and `AUTONOMY_READINESS_20261016.md`.

## 2. Authority and scope

- No delegation, coding workers or auxiliary model calls. The current assistant implements directly after approval, using vertical RED/GREEN tests.
- Keep typed beta model/tool execution, untrusted Telegram dictionaries, governance/creation and closed HTTP business routes denied. No provider switch, paid fallback, live smoke, merge, push, restart or deployment.
- Butler remains the human gateway, not a planner, peer governor or source of execution grants. Required audit acknowledgement does not authenticate a caller or grant a resource.
- Keep browser isolated chat tool-, memory-, thread- and Lattice-task-free. Preserve A1 context boundaries and A2 immutable report/body/task bindings.
- Existing ordinary `AuditLog` is not promoted to a durable task journal. Its acknowledgement may be in-memory or WAL/NORMAL. Concrete `BetaAuditLog` requirements remain stronger and unchanged.
- No new database, table, migration, network endpoint, inbound field, provider quota, role, peer policy or tool is introduced.

## 3. Existing reproduced defect

The actual isolated gateway returned `completed`, with an A2 report, after two injected audit exceptions. Its routing callback ran once and the real echo execution ran once. This is synthetic offline evidence, not a live-provider test. In the current routed path, routing also precedes its first audit, and successful conversation persistence precedes final gateway audit. `_audit_append` currently catches errors and continues.

## 4. Error and acknowledgement contract

Add exported `ButlerAuditError(RuntimeError)` in `agency.butler.service`. It exposes only the fixed message `butler audit unavailable`; it carries no prompt, output, sender, database path or underlying exception body. Raise without displaying the underlying exception chain.

Keep `_audit_append(*, agent, action, result, target=None, evidence=None) -> None` unchanged for callers. Construct one `AuditEntry`, call `self._audit.append(entry)` exactly once, and require an exact string acknowledgement equal to `entry.entry_id`. None, False, arbitrary truthy values, a foreign ID and exceptions all fail with `ButlerAuditError`. Do not retry an append: it may already have committed. Cancellation propagates as cancellation, never success, and is not swallowed by generic execution handlers.

Logging on this boundary uses fixed event names, fixed phase/action codes and exception class only. No `log.exception`, traceback locals or exception text. Required audit records on these gateway paths contain identifiers generated by the system, fixed action/target codes, lengths and durations only, not user bodies, response bodies, arbitrary sender strings or command arguments. Use agent IDs/task IDs where needed; the execution target must no longer be a free-form task title containing user material. This is a repair of these call sites, not a claim that every legacy log/store is privacy-safe.

## 5. Required ordering

### Routed `handle_message`

1. Preserve beta denial before startup and all existing input/owner/thread checks. Initialization is not a model dispatch.
2. After validation and explicit thread authorization, require a sanitized `butler.request` acknowledgement before deterministic command mutation, recalled-content access, routing or task creation.
3. Preserve deterministic command routing, owner-scoped active-thread behavior and context assembly. No new model call is added.
4. Route, require the existing route acknowledgement, execute, and require final `butler.handle_message` acknowledgement **before** saving the conversation turn/thread messages or returning it.
5. `ButlerAuditError`, `MeteredDenied` and `MeteredError` propagate as blocking errors before ordinary execution-error rendering. Never turn them into a completed reply or a deterministic routing fallback that starts further work.
6. Preserve ordinary non-audit/non-metered failure rendering as failed/timeout diagnostics. No new claim that a timeout means no remote effect. Failure logs contain exception class, not private bodies/tracebacks.

### `route` and `execute` direct callers

`route` requires a sanitized `butler.route_intent` acknowledgement before invoking a configured/injected routing model or deterministic router. This also protects direct callers, not just `handle_message`. Metered denial/uncertainty and audit failures do not trigger its legacy fallback. Ordinary legacy routing failures may still select the deterministic router; record only exception class.

`execute` retains typed beta denial, then requires `butler.execute_intent` acknowledgement before submitting a task. Its existing terminal audit must acknowledge before returning output. Propagate audit failures without a success-shaped response. The caller must not accept an exception string as generated output.

### Isolated `handle_isolated_message`

After existing input checks, require a sanitized `butler.isolated_request` acknowledgement before routing. Keep route/outcome audit acknowledgements required. Failure of any of these raises `ButlerAuditError`; no `ButlerReply(status="completed")`, output or assessment is returned. Preserve actual execution status on ordinary failed turns and all existing isolation exclusions.

### Deterministic thread commands

The request preflight must acknowledge before command mutation; the command outcome audit must acknowledge before success is returned. A post-mutation audit failure is an uncertain acknowledgement, **not rollback**. Do not retry the command within this request. Direct use of private helpers is not an exposed authenticated ingress.

## 6. Consumers

- Prototype `/api/chat`: catch `ButlerAuditError` explicitly, before the generic exception logger. Return HTTP 503 with the fixed message `Audit unavailable; execution outcome unconfirmed. Do not automatically retry.` No raw output, report, exception body or successful response. Keep host/origin/CSRF/body validation and isolated-only dispatch unchanged.
- Telegram nonbeta normal chat and private thread-command paths: catch that typed error, attempt at most one fixed failure reply and return `status="rejected", reason="audit unavailable"` after successful delivery. This is a terminal handling/delivery outcome, not a completed execution. The legacy poller advances rather than retrying model execution merely because an audit-failure notice was delivered.
- `process_message`: return the fixed failure notice on that typed error, with no model/demo fallback. This string-returning legacy API cannot express execution truth and is not an autonomous admission API.
- Do not route `/research` through a different execution path merely to make this patch broad. It currently calls the orchestrator directly and remains an explicitly tracked A3 integration gap; neither this repair nor its tests certify that path as task-wide admitted/metered.
- Failed Telegram delivery, cursor loss/restart and other callers can still be uncertain. A3.1 adds no durable outbox or general request deduplication. Do not claim exactly-once execution or delivery.

## 7. Cross-store limits

Required ordering prevents a gateway success transcript from being written before final gateway audit acknowledgement. It does not make independent stores transactional. An earlier orchestrator execution-memory write, evidence finding, already-mutated thread command or provider call can survive a later gateway failure. Preserve that uncertainty and existing A2 provenance; never delete evidence or pretend the external effect was undone.

A second failure during optional conversation persistence is not retroactively a proof of successful persistence. Existing best-effort conversational recall/transcript semantics remain unless a separate approved storage contract changes them. No durable recovery/reconciliation or total audit-privacy claim is made.

## 9. Acceptance cases
